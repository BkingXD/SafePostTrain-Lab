# 大模型后训练：从需求到交付的完整流程

这份指南把 17 个学习模块连接成一条可执行的工程链。它描述一种可审计的路线；不同模型并不一定使用所有阶段，任何训练效果都需要通过各自实验验证。

## 1. 先把问题、模型和验收标准固定

1. 定义模型的使用场景、用户、允许/不允许的行为、正常能力与成本约束。安全目标至少同时看有害完成、合法问题误拒绝和一般能力保持。
2. 选择具体模型 **ID + 精确 revision**，确认模型卡、许可证、tokenizer、chat template、精度与硬件要求。Base 模型和已有对齐的 Instruct/Thinking 模型起点不同，不能把原模型已有能力记为本次训练收益。
3. 冻结训练/开发/最终测试的来源分组和评测协议；写下安全变化、误拒绝及能力退化的容忍范围。开发集可用于排错和调参；最终测试参与调参后就不能继续当作独立测试。
4. 记录运行环境：GPU、驱动、PyTorch/CUDA、训练库版本、有效上下文长度、batch、随机种子、时间和预算。先在小样本检查整个链路。

## 2. 读懂每个环节的输入和产物

| 阶段 | 主要输入 | 参数是否更新 | 主要产物 | 决策依据 |
|---|---|---|---|---|
| 原模型基线 | 已冻结模型与测试协议 | 否 | 原始回答、分项指标与成本 | 确定改进空间和失误类别 |
| 数据工程 | 原始任务、授权数据与标注规则 | 否 | 消息、偏好、轨迹、来源及数据卡 | 质量、污染、覆盖和分组 |
| SFT | prompt、目标 completion | 是 | 模型或 adapter、优化器、训练日志 | 有效标签、生成与开发集表现 |
| 偏好优化 | 同一 prompt、chosen、rejected，参考策略 | 是 | DPO 等策略及参考配置 | margin、各侧概率和独立行为评测 |
| 在线优化 | 当前策略 rollout、可计算反馈、参考策略 | 是 | PPO/GRPO 策略、采样与奖励记录 | 奖励各分量、KL、熵、长度、成本 |
| 筛选与蒸馏 | 教师生成、验证规则或分布 | 筛选否；学生训练是 | 候选集、筛选记录、学生权重 | 覆盖、错误、学生独立表现 |
| 最终评测与交付 | 冻结模型、独立测试及裁判 | 否 | 原始回答、分组指标、模型卡 | 安全、能力、成本与不确定性 |

这条顺序用于理解依赖关系：先定义目标和基线，再处理数据，之后才选择训练与评测。DPO、PPO、GRPO 是优化方法；人工、模型或规则分别是反馈来源；RLVR 描述一类可验证反馈。它们不在同一个互斥列表里。

## 3. 数据：从结构到可追溯

- SFT 需要一个 prompt 和完成该任务的目标回答；可使用对话消息 `[{role, content}, ...]`。先用正确的 chat template 序列化，再确认哪些 token 作为监督标签。
- 偏好训练需要同一 prompt 的 chosen/rejected，并记录选择原因。只按拒绝词或长度标注会把代理目标当成安全判断；合法敏感请求需要有用回答，有害意图需要适当限制。
- 在线训练需要 prompt、环境/验证目标及奖励接口；每次生成另记策略版本、采样参数、完整输出、各奖励分量与失败状态。
- 工具训练多出工具 schema、调用参数、返回消息与环境状态。将工具返回视为不可信输入，只在可恢复的沙盒环境演示。

按原始问题、意图、来源或攻击家族分组后再生成改写，避免同源样本跨训练/测试。分别记录样本数、有效监督 token、长度分布、丢弃和截断；样本行数相同不代表 token 预算相同。数据卡包括来源、许可证、版本、标签规则、去重、分组、人工复核与局限。

### 一个对话标签检查

例如模板序列为 `[用户标记, 问题, 助手标记, 回答, EOS]`。assistant-only 训练通常将 prompt 标签设为 `-100`，回答和 EOS 保留；模型在助手标记位置预测回答首 token。真实模型的标记及结束符由 tokenizer 决定。打印 token/label/mask 并检查后再启动大规模训练，避免重复 shift 或所有标签都被屏蔽。

## 4. SFT、LoRA 和偏好优化各做什么

SFT 的核心是对有监督位置计算负对数似然，反向传播后更新全参或部分参数。LoRA 把某些矩阵的增量写作 `(α/r)BA`，通常冻结原矩阵；QLoRA 又将冻结底模以量化形式存储，但总显存还包括激活、梯度、优化器、非量化参数与运行库。

DPO 比较 chosen 和 rejected 相对于参考策略的对数概率增量：`Δ=(logπθ(chosen)−logπref(chosen))−(logπθ(rejected)−logπref(rejected))`，经典损失为 `−logσ(βΔ)`。需要同时观察两个回答的绝对 log-prob、长度、margin 和真实生成；只看偏好 loss 下降会漏掉 chosen 概率也下降的失败。参考模型、模板、token 聚合和截断必须固定。

PPO 需要 actor、采样时的旧策略 log-prob、参考策略、反馈源和通常的 critic；GRPO 利用同一 prompt 的组内反馈估计相对优势。在线训练还要记录 rollout 策略版本、生成 token、验证器调用、KL、熵、截断及全组同分比例。不同实现的 token/回答归一化、KL 估计、采样和裁剪可能不同，不能仅凭算法名字判断它们一致。

## 5. 一次安全后训练的最小对照

在同一模型与冻结评测协议下，依次比较：

1. E0：原始模型；E1：安全 SFT；E2：E1 加标准 DPO。
2. E2-control：使用偏好 chosen 回答继续 SFT，控制额外训练预算，检验收益是否仅来自优质回答。
3. E3：使用合法/有害双向边界偏好的 DPO，控制有效 token 与超参搜索预算，研究误拒绝和有害完成的共同变化。
4. E4：只从训练/开发侧失败中挖掘数据；与相同新增数据量和训练预算的随机扩充比较。未参与迭代的攻击家族留作最终测试。
5. 预算与奖励质量允许时才加入在线 RL 或第二个模型。报告生成、裁判与训练三类成本，不把全部收益归给单一算法。

如果最终测试又驱动了数据或超参调整，该测试已变成开发集。负结果仍应留在表中，尤其是“偏好目标改善但生成质量退化”的情况。

## 6. 评价、误差分析与交付

[HarmBench](https://github.com/centerforaisafety/HarmBench)、[XSTest](https://arxiv.org/abs/2308.01263)、[StrongREJECT](https://arxiv.org/abs/2402.10260) 可分别用于研究有害行为、误拒绝与回答是否包含实质性有害内容，必须遵守各自原始协议；[lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness) 可固定通用能力评测实现。

每条评测记录应保留样本 ID、来源版本、模型及 adapter revision、模板、解码设置、原始回答、分项判定、评分器版本与超时/错误。多次攻击对应同一行为时，按行为组重采样；ASR@预算与每次尝试的成功率分母不同。对裁判进行分层人工抽检，并报告不确定性和语言/风险切片。

最终交付包括训练配置、数据清单、分阶段 adapter/权重、依赖锁、原始输出、复算脚本、模型卡、数据卡、失败案例与资源记录。部署、量化或合并 adapter 后需要重新检查模板、输出一致性、安全和普通任务。完整在线 PPO 的恢复还需 critic、优化器及 rollout 等状态。
